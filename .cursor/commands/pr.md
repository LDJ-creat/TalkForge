# PR（Pull Request）提交规范
## 一、核心原则：单一职责提交
所有新增功能、代码修改需基于 PR 提交，严格遵守一个 PR 只做一件事原则，保证提交粒度精简、清晰可控：
- 每个 PR 仅实现或修改单一功能/单一逻辑优化点，禁止多功能、多改动混合提交
- 优先提交小粒度、细范围的精简 PR，降低代码合并、审查、回滚成本
- 大型功能、复杂需求必须拆解为多个独立、可单独上线的 PR，分步骤迭代提交
## 二、PR 必填内容规范
PR 标题与描述必须完整、清晰、无歧义，便于审核者快速理解改动内容，固定包含以下四项内容：
1. PR 标题
一句话精准概括本次 PR 的核心改动，明确新增功能、优化点或修复内容，简洁直观、无冗余。
2. 功能描述
详细说明本次新增/修改功能的核心作用、业务价值，同时补充功能的具体使用方式、适用场景，让审核者清楚改动的业务意义。
3. 实现思路
简要阐述本次改动的技术选型、核心逻辑、关键实现方案，重点说明核心代码思路、特殊处理逻辑、技术取舍原因，无需冗余贴代码，突出核心设计即可。
4. 测试方式
明确说明验证本次功能有效性的测试步骤、验证场景、校验标准，包含正常场景、边界场景测试方式，确保改动功能可复现、可验证、无问题。
